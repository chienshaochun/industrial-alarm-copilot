# Incident Gap 分析

## 1. 目的

本文件以同一設備內相鄰警報的時間間隔，選擇第一版 incident 分組門檻。這個門檻是可調整的工程假設，用來建立一致且可重現的分析單位，不代表真實故障、修復或停機的物理邊界。

## 2. 計算方式

事件先依下列欄位穩定排序：

1. `machine_id`
2. `timestamp`
3. `source_row`

接著只在同一設備內計算：

```text
gap = 目前事件時間 - 前一事件時間
```

20 台設備的第一筆事件沒有前一事件，因此 444,834 筆事件共產生 444,814 個有效 gap。

分布具有明顯長尾：中位數不到 1 分鐘，但最大間隔約 291.5 天。平均值受到少數極長沉默期影響，不適合直接作為 incident gap。

共有 83 個零分鐘 gap，數量與完全相同事件群組數一致。原始事件視圖仍保留這些記錄，不在 gap 分析階段刪除。

## 4. 候選門檻

切分規則統一為：

```text
gap <= threshold：留在同一 incident
gap > threshold：開始新的 incident
```

## 5. 第一版決策

預設使用 30 分鐘，並以 15、30、60 分鐘進行敏感度比較。

選擇理由：

- 30 分鐘略高於 90% 分位數 25.36 分鐘，具有直接的資料依據；
- 15 分鐘會產生 68,060 個較碎的 incidents，平均約 6.54 筆事件；
- 30 分鐘會產生 38,116 個 incidents，平均約 11.67 筆事件；
- 60 分鐘只產生 19,002 個 incidents，平均約 23.41 筆事件，增加合併不相關警報的風險；
- 38,116 個預估 incidents 足以支援後續檢索與時間序列評估。

設定保存在 `configs/default.toml`：

```toml
[incidents]
gap_minutes = 30
sensitivity_gap_minutes = [15, 30, 60]
```

## 6. 解讀限制

- gap 是沒有警報記錄的沉默時間，不等於設備正常、停機或完成維修；
- ALPI 沒有 incident、根因、clear/reset 或維修標籤，無法直接驗證 30 分鐘是真實邊界；
- 所有模型評估都必須記錄實際使用的 gap 設定；
- 15、30、60 分鐘的結果若差異顯著，應在最終報告揭露敏感度，而不是只呈現最佳結果。

## 7. 重現方式

Gap 計算與門檻比較由下列函式建立：

- `add_inter_event_gaps()`
- `build_gap_threshold_profile()`
